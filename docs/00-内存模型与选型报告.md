## 1. 内存模型

### 1.1 三层表示与两套编号

RSupercell 的一个变量在三个层次上有三种身份，这是全局理解的枢纽：

| 层 | 身份 | 载体 | 生命周期 | 谁负责 |
| --- | --- | --- | --- | --- |
| **源码层（用户可见）** | 键名 + 本地别名 | `receive(n) as (num)` | 书写期 | 用户 |
| **静态层（编译器私有）** | `KeyIdx` (u16) 全局键号 / `VarId` 字母串 本地变量号 | 键表 / `v_<id>` | 编译期 | 编译器 |
| **运行层** | `VarHandle` 三态之一 | Packet 槽位 / Env 局部 | 运行期 | 运行时 + rustc |

**为什么必须是两套编号（§10.1 的关键点）**：

- `KeyIdx` 是**跨 Cell 全局去重**的：整个程序里所有出现过的键名（`n`、`sum`、`res`…）被 intern 成 `0,1,2…`。Packet 用 `Vec<Option<VarHandle>>` 按 `KeyIdx` 索引，于是"传参"退化成一次数组下标写，而不是字符串哈希查表。这是 §17.1「砍掉 70% Packet 开销」的全部来源。
- `VarId` 是**每 Cell 独立**的：cell `fact` 的别名 `num` → `v_a`，cell `worker` 的别名 `data` → `v_a`。两者完全隔离、互不冲突。这正是"不同 Cell 实例即使别名重名也互不干扰"（设计文档 §2.4）的实现基础——**它靠的是"每实例一个独立栈帧 + 每 Cell 一套独立的局部变量名"，而不是靠运行时做重命名**。

**推论（很重要）**：`VarId` 隔离这件事**在类型化调用约定下自动成立**，不需要任何运行时支持。设计文档 §7.5 说"每个消息包附带映射表：用户别名 → 底层唯一变量 ID"，这是**类型擦除路径**才需要的额外机制；类型化路径下，目标 Cell 的形参就是编译期写死的 Rust 局部变量，映射表不存在也不需要。

### 1.2 实例与帧：什么会新建运行时实体

> ⚠️ **本表是我方裁定后的结果，不是《语言设计文档》§4.2 原表的搬运**。原表只有 4 列（是否新建 Cell 实例 / 是否跨边界 / 是否需要 Packet），没有"新建 async 任务"这一列；`jump recurse` 一行与原文正面冲突，详见 **B12 与裁定 D3**。

| 语句 | 新建 Cell 实例 | 新建 async 任务 | 跨边界 | Packet |
| --- | --- | --- | --- | --- |
| `jump T go with(..)` | ✅ | ❌（内联调用） | ✅ | 类型化路径下 ❌（§2.2） |
| `jump loop` | ❌ | ❌ | ❌ | ❌（位置刷新） |
| `jump recurse T` | ✅ | **默认 ❌（内联 await）；仅当下一条不是紧邻 `jump sync` 时才 ✅ spawn**（D3） | ✅ | 类型化路径下 ❌ |
| `jump and T1,T2` | ✅ | ✅（真并行） | ✅ | 类型化路径下 ❌ |
| `jump sync g` | ❌ | ❌ | ❌ | ❌（收集） |
| `exit go with(..)` | ❌ | ❌ | ✅（交回父） | 类型化路径下 ❌（直接返回类型化结构体） |
| `die` | ❌ | ❌ | ❌ | ❌（类型化路径 = `None`） |

**与原文的冲突（必须知道，否则会实现错）**：《开发说明》§3.4.2③「生成全新子实例（**独立 async 任务**、独立环境）」、§12.1 映射表「`jump recurse T` → `let r = Group::spawn(cell_t(pkt))`」、《语言设计文档》§5.1/§5.4「**独立任务**」——三处都要求 recurse 必须 spawn。本项目按 **D3** 改为"默认内联 await"：当 `jump recurse` 的下一条语句**正是** `jump sync <同一 group>` 时，父在其间没有任何可观测行为，spawn 与内联语义等价，而内联省掉一次任务分配。若父在 sync 之前还要继续做事（§5.4 允许），则仍按原文 spawn，保持并发语义。

**栈/堆真相**：

1. **Rust 不做尾调用优化**。`jump T go with(a)` 生成 `return cell_t(arg_a).await;`——父 future 会一直挂起持有自己的全部局部变量，直到子返回。所以**一条 N 层的跳转链 = N 层嵌套 future 的内存**，总占用 O(链深 × 帧大小)。**已实测验证**（探针：每层持有 1 MB 局部，链深 1/4/16 时峰值存活层数分别为 1/4/16；若存在 TCO 应恒为 1）。这不是 bug，是 AOT 编译到 Rust 的固有代价，必须写进用户文档（长跳转链请用 `jump loop` 或 `extern rust` 热点下沉）。
2. **`async fn` 自递归必须装箱**。`cell fact` 用 `jump recurse fact` 时生成 `cell_fact(cell_fact(n-1).await)`，这是递归的不透明类型，`rustc` 直接报 `E0733 recursion in an async fn requires boxing`（已实测）。必须生成 `Box::pin(cell_fact(..)).await` 或 spawn。**这是文档 B9**：A.2 阶乘 recurse 版按字面翻译是编译不过的。代价 = 每层 1 次堆分配。
3. `jump and` 的**真并行**才需要独立任务；`jump recurse` 仅在非紧邻 sync 时才需要（见上）。

### 1.3 所有权状态机（每 Cell 每语句）

```
        receive 键
            │
            ▼
        ┌────────┐   go with / exit go with   ┌────────┐
        │ Active │ ─────────────────────────► │ Moved  │（不可再用）
        └───┬────┘                            └────────┘
            │  read with
            ▼
        ┌────────┐
        │ Frozen │（只读、禁止 move、禁止修改）
        └────────┘
```

- `Active → Moved`：所有权转移（move），与 Rust 语义一致。后续引用 → RSC-E060。
- `Active → Frozen`：`read with` 分发，之后只读。move → RSC-E061；透传区引用 → RSC-E062。
- **Frozen 不可逆**，且只能继续 `read with` 转发（引用链 +1）。
- 状态在 `jump loop` 处**回滚到入口快照**（同一实例复用环境）。
- 状态只作用于 **receive 别名**（即 `v_*`），`let` 局部变量完全交给 rustc（§10.3 末句）。

**为什么 Arc 句柄不能出现在 `go with`（RSC-E064）**：`go with` 的契约是"独占转移所有权"，而 Arc 句柄是"引用计数 +1 的共享引用"。让它走 `go with` 会让源实例的局部变量在 `go with` 之后仍被下游读到，与 move 语义直接矛盾。类型化后这条检查退化为一条简单规则：**曾经 `read with` 过的变量，只能出现在 `read with` 实参位置**。

### 1.4 生命周期：Packet 的生灭

```
send 侧:  实参求值 → VarHandle(Owned) / Arc::clone → 写入 Packet 槽位
              ↓ (跨边界)
recv 侧:  receive 按 KeyIdx 取出选中槽位 → 移入本地环境变量
              ↓
         Packet 立即 drop：未选中槽位随 Packet 释放
              ↓
         变量从此就是普通 Rust 局部值，不再有任何 Packet/VarHandle 参与
```

关键点：

- **选择性接收是"白名单 + 立即销毁"**，不是复制。`receive(x, log)` 没写的 `y` 在 Packet 析构时被 drop，零残留。
- **`die` 不产生返回包**。父的 `jump sync` 收到的是 died 标记包 → 键缺失。这是 S3 要解决的问题。
- **Arc 数据存活 ≫ 任务存活**。`jump sync` 结束 ≠ 引用归零；多层转发时 C 结束只减 1，数据要等引用链全部 drop 才释放（设计文档 §4.5）。所以**不要用"sync 返回了"推断"内存还回去了"**。

### 1.5 调度模型

- 单进程、单 runtime、整条业务流程在同一个 executor 内流转（§1.4、§14）。
- `jump and` = 真并行任务 + group 管理；`concurrent_limit` = 信号量 + **惰性 spawn**。
- 惰性 spawn 的真正含义：**拿到令牌才 spawn**，而不是"先建好 10⁷ 个任务句柄再慢慢跑"。文档 §12.5 的伪代码前半段是对的，但 `Group` 用 `Vec<JoinHandle>` 累积句柄，**仍然会为每个元素留一个句柄**（D4/B4）：10⁷ × (JoinHandle + 已完成任务槽位) 依然是数十 MB 到 GB 级。正确做法是完成即回收（见 §4.3 风险 3）。

### 1.6 六个必须先讲清的语义细节（我已逐条裁定）

1. **`receive` 是"入边契约"而不是"我要什么值"**。契约检查（C1）要求：`receive` 的每个键必须出现在上游 `jump` 实参的键集里。`over`/group 的返回包键不在任何入边上——这与 A.2/§7 的示例冲突，裁定见 S4。
2. **`jump loop` 是唯一不按键名的传参**：按位置刷新 receive 列表（§9.2）。实参个数必须 == receive 键数（RSC-E041）。
3. **只有 plain `jump` / `exit` / `die` 是出口**。`recurse` / `and` / `loop` / `sync` 都不是（《语言设计文档》§8.2"三类出口"，并见开发说明 §11.2 的 CFG 伪代码）。收敛检查必须按这个语义做，否则会把"派生后忘了 exit"漏过去。
4. **`die` 的返回**：设计文档 §8.2 说"不产出任何返回包"，开发说明 §13.1/§13.4 则用 `Packet::none() + died 标志` 表达。本项目按 S2 统一为**类型化的 `None`**（`async fn cell_x(..) -> Option<Ret_x>`），两种表达在类型化后等价。这是两份文档的第二处措辞冲突，一并记录；多包 receive 缺键的后果按 S3 处理。
5. **冻结是单向的**。一旦 `read with`，该变量在本 Cell 内终身只读。
6. **Env 是实例私有的**。`jump loop` 是唯一会"跨迭代改写环境字段"的语句（位置刷新），其他语句都不会让两个实例看到同一份内存——这就是 CSP 承诺的全部机制。

## 2. 选型

### 2.1 S1：async runtime —— ✅ 已确认：标准库自研极简 executor（零外部依赖）

**问题**：生成物是"单个 .rs 文件 + `rustc` 编译"（§15.2），但设计文档 §12 决定 1 选定 **Tokio**。这两者冲突：Tokio 不是一个能裸用的模块，`rustc main.rs -o out` 找不到 `tokio::spawn` 就会失败。必须额外满足其一：

- (a) 预编译一个依赖 Tokio 的 runtime crate，调用时补 `--extern` + `-L dependency=<deps 目录>`（需要为目标平台预编译整套依赖树，换 target 就要重编）；
- (b) 改为 `cargo build` 编译生成物（§16.2 提到"配合 cargo 增量编译"，但 §15.2 写的是裸 rustc，两处不一致）；
- (c) 运行时零外部依赖。

**推荐 (c)：标准库自研极简 executor**。理由：

| 维度 | 自研 std-only | Tokio + --extern | cargo build |
| --- | --- | --- | --- |
| 生成物依赖 | **0**（`rustc app.rs -O -o app` 直接可跑） | 需预编译整套 tokio 依赖树 | 需 cargo 工程 + 锁文件 |
| 交叉编译 / 换 target | 直接可用 | 需为目标重新预编译 | 需联网或 vendored registry |
| 任务 spawn 成本 | 可控（我们决定是否装箱、是否池化） | 成熟优化 | 同 Tokio |
| 我们的工作量 | 约 400 行：Waker(vtable) + 线程池 + 队列 + parking | 少 | 中 |
| 风险 | 需自己写对 async 唤醒（**有测试兜底**） | 依赖树/版本漂移 | 离线构建 |

自研 runtime 的**硬性要求**（我会照此实现并配测试）：`RawWaker` vtable 正确性、`spawn`/`Join`、多线程 worker + 全局队列（Mutex + Condvar，worker 空闲时 park）、`Group` 的增量回收、任务 panic 不污染父（用 `catch_unwind` 或 `JoinHandle` 隔离）。这是**真实工作量但完全可控**，且替换点仍然收敛在模板层（§20 风险 1 的承诺不变）。

### 2.2 S2：Cell 调用约定 —— ✅ 已确认：静态类型化 monomorphized 调用（本报告最重要的一条）

**问题**：文档 §13.1 的运行时模板用 `VarHandle` + `Box<dyn Any + Send>` 做类型擦除。这带来两个硬问题：

1. **接收端没有类型就无法 downcast**。`Box<dyn Any>` 取出时必须知道具体类型 `T` 才能 `downcast::<T>()`。而 `receive(n);` 不带类型注解是文档允许的写法（§3.4.1 `receive(x);`）→ **类型擦除路径下无法确定 `T`**。这不是"可以交给 rustc 兜底"的问题：rustc 也无法从 `Box<dyn Any>` 里推出 `T`。
2. **即使标注了类型，堆分配也消不掉**。文档 §17.1 的"静态类型特化 pass"说会"生成专用 `set_<type>` 绕过 `dyn Any`"，但只要槽位类型还是 `VarHandle`，`Box::new(x)` 这一次分配就还在，`Vec<Option<VarHandle>>` 的 memset 也还在。

**量化**：单次 plain `jump`（2 个实参，全局 20 个键）的类型擦除路径成本 ≈ 3 次堆分配 + 3 次释放 + 480 字节 memset ≈ **60–120 ns**（推算）。手写等价 Rust 是 **0**。也就是说：任何"单次跳转里业务计算 < 1 µs"的场景，性能比就是 2–3 倍，`≥90%` 目标**不可能达成**。

**推荐：S2-类型化**。生成物形态：

```rust
// 每个 Cell 生成一个类型化 async fn：参数即 receive 键，类型由 D2 裁定解析
async fn cell_fact(n: i64) -> Option<Ret_fact> { ... }        // die ⇒ None
struct Ret_fact { res: i64 }                                  // exit go with 的输出契约

// plain jump：零分配，参数按值 move
return cell_even(v).await;

// read with：类型化共享句柄，无需类型擦除
let shared: Arc<Vec<u8>> = data;                    // go with → move
g.push(async move { cell_w(Arc::clone(&shared)).await });
```

- 零堆分配、零 `dyn Any`、零 Packet（除非显式开启动态后端）。
- `§12.8 小任务内联` / `§17.1 静态类型特化` 两个优化项**变成默认行为**，不需要额外的 pass 去"追回"性能。
- `VarHandle` 运行时**保留**在 `rscel-runtime` crate 中并按 §13.5 完整实现与测试（满足文档要求），gen 提供 `--dyn-packets` 开关走类型擦除路径（默认关闭）。两条路径语义等价，由 gen 保证。

**代价**：gen 必须实现一个类型来源解析（D2）。这是实打实的工作量，但没有替代方案——想要 ≥90% 就必须有静态类型。

### 2.3 S3：`die` 时父侧多包 receive 缺键 —— ✅ 已确认：契约期静态拒绝

§13.4 写的是"首版保守：die 的子实例键缺失时取默认值（`Option::unwrap_or(Default::default())）"。但：

- `Default` 是额外 trait 约束，会让用户的 `struct Order` 之类类型编译失败；
- 静默给业务塞默认值，是**制造错误数据**而不是暴露 bug。

**推荐：契约期静态拒绝**。前端在**检查 C1（契约表构建）**阶段已知每个 Cell 的全部可达出口集合：

- 若子实例 W_i **不存在任何** `exit go with`（即只会 die），而父侧 `receive(g1.W_i.*)` 引用了它 → 报 RSC-E042/E044 类错误，提示"该子实例只会 die，不可能返回键 X"；
- 若子实例 W_i **可能** exit 也可能 die（多分支），父引用它的键 → 同样报错，提示把 die 分支改成 `exit go with` 或拆成两个 Cell。

这样多包 receive 就有了"**全路径可满足**"的强契约，父侧解包可以 `expect()` 硬失败，永不产生静默默认值。`die` 只在"父侧不引用该实例任何键"时使用。

**备选 (b)**：注解写 `Option<T>`，die 时为 `None`；**备选 (c)**：维持 §13.4 的 `Default::default()` 并强制 receive 注解类型实现 `Default`。

### 2.4 S4：多包 `receive` 的时序 —— ✅ 已确认：late binding

设计文档 §7.2 / 附录 A.2 写：

```text
cell parent;
receive(g1.W1.A, g1.W2.A) as (a1, a2);   // ← 声明在 cell 开头
let data = [10i64, 20i64];
jump and worker over data group g1;        // ← g1 在这里才被创建
jump sync g1;
out(a1, a2);
```

**这在时序上不可能**：`receive` 位于 Cell 入口，但 `g1.W1` 这个包要等到 body 执行到 `jump sync g1` 才存在；而且 §3.4.1 规定每个 Cell 恰好一条 `receive` 且紧跟 `cell`，没有第二个声明位置。

**推荐裁定 S4（late binding）**：`receive` 的两类键分开处理，语法不变、语义补全：

- **裸键**（`receive(a, b)`）：入边契约，函数入口从入口 Packet 解包；
- **包限定键**（`receive(g1.W1.A)`）：**组内扇入契约**，由 gen 在对应 `jump sync g1` 之后生成解包：
  ```rust
  let mut w1 = pkts[0]; let a1 = w1.take(K_A).expect("contract");
  ```
  检查 C1 校验时，该键不与入边比对，而是与"组内子实例 W1 的输出契约"比对（§11.1 的 `outputs[子实例]` 分支本来就是这个语义，只是 `edge_keys` 的角色被 `jump sync` 取代）。

代价：静态检查里 `receive` 的一小部分语义依赖 body 里的 `jump sync` 出现位置（需要一次"先建 group 定义、再校验 receive"的固定点或单遍两阶段）。这是可接受的。

### 2.5 D2：接收类型来源

`receive(n: i64)` 有注解时直接用；无注解时按顺序解析：

1. 收集该 Cell 的**全部入边实参表达式**（plain/recurse/and/over 各边）与其类型；
2. 所有边类型一致 → 采用；出现两种不同类型 → 报 RSC-E038（需要注解）；
3. 某边类型自身不可解析（例如实参来自 `extern rust` 里的复杂泛型调用且无注解）→ 同样 RSC-E038，**不猜**。

轻量的双向类型传播只做"字面量 / 局部变量 / 形参 / 单调用链"这一层，**不引入完整 HM 推导**。类型不可知时报错要求注解，比猜错更好——符合"有就是有，没有就没有"。

### 3.2 附录 A.2 阶乘（recurse 版）的正确写法

```text
cell fact;
receive(n) as (num);
let mut sub: Option<i64> = None;
jump recurse fact when num > 1 go with((num - 1) -> n) return(res -> sub) group r1;
jump sync r1;
exit go with(sub.unwrap_or(1) * num);
```

- `fact(1)`：不派生 → `sub = None` → `unwrap_or(1) * 1 = 1` ✅
- `fact(5)`：逐层 4·3·2·1 → 120 ✅
- 键名契约完整：`go with((num - 1) -> n)` 的非标识符实参显式给键（§9.1 规则 1）；`return(res -> sub)` 把子返回包的 `res` 映射回父变量 `sub`（`let mut` 因此必需）。

实现时附录 A 全部样例按"能独立编译运行的完整程序"交付（补 `cell main` 入口，否则会触发 RSC-E020）。

## 4. 性能模型

### 4.1 单操作开销

**已实测**（2026-09-27，本机 rustc 1.97.1 `-O`，500 万次循环取均值，零外部依赖；基准程序 `scripts/bench/packet_overhead.rs`。下表为**连续 3 次运行的区间**，同一次运行内的数字才可直接相减）：

| 操作 | 实测区间 | 说明 |
| --- | --- | --- |
| **A. 类型擦除 Packet**（20 键 plain jump，2 个 `i64` 实参，含构造+析构） | **85 – 90 ns/次** | 1 次 `Vec` 分配 + 480B memset + 2 次接收端运行时匹配 + 析构 |
| **B. 类型化直接传参**（同语义 plain jump） | **1.0 – 1.2 ns/次** | 参数按值传递，零分配 |
| **A−B 固定开销** | **约 85 – 89 ns/次（69 – 89×）** | 类型擦除的**每次跳转**固定成本 |
| **C1. `read with` 一次转发**（1 次 `Arc::clone` + 1 次 drop） | **12.2 – 12.8 ns** | 这是 `read with` 的**单价** |
| **C2. 两次转发**（2 inc + 2 dec） | **21.1 – 22.1 ns**（C1 的 1.68×，非严格 2×，差额为循环与传参固定开销） | 用于验证近线性 |
| **C1×3. 三层转发**（附录 A.7 的 `a→b→c`） | **约 37 – 38 ns** | = 3 × C1 |

> ⚠️ **口径更正（本版修订）**：初稿把"21.2 ns"当作 `Arc::clone` 的 +1 单价，据此推出"三层转发 ≈ 128–132 ns"，**高估约 3.7 倍**。原因是基准 C 循环每次迭代实际做了 **2 次 inc + 2 次 dec**（外层传参 clone + 函数内 clone），却被标成 "+1"。已修正基准程序：现在 C1 精确测 1 inc + 1 dec = 12.2–12.8 ns，三层转发 = 3 × C1 ≈ 37 ns。**§4.1 推算表的 `read with` 三层转发一行同步改为 37–38 ns。**

基准程序（`scripts/bench/packet_overhead.rs`）单次运行的保持率表（本次 a≈88.2 ns、b≈1.0 ns）：

| 单次跳转的业务计算耗时 | 类型擦除路径性能保持率 | §17 要求 ≥90% |
| --- | --- | --- |
| 10 ns | 11.2% | ❌ |
| 50 ns | 36.9% | ❌ |
| 100 ns | 53.7% | ❌ |
| 1 µs | 92.0% | ✅ 勉强 |
| 10 µs | 99.1% | ✅ |

> 写基准时又被 B10 咬了一次：接收端拿到 `VarHandle` 后**不能**直接取值，必须写 `match`（真实实现还要 `downcast::<T>()`）。槽位里只有一个 `u64`，接收端无从知道它是 i64、f64 还是 bool——这不是理论问题，是编译期就撞上的类型错误。

**推算**（其余行基于上述实测单价外推，非实测）：

| 操作 | 类型化路径（S2） | 类型擦除路径（文档字面） | 手写 Rust 对照 |
| --- | --- | --- | --- |
| plain `jump`（2 实参） | **1.0 – 1.2 ns（实测）** | **85 – 90 ns（实测）** | 0 |
| `jump loop` 一轮 | ≈ 0–2 ns（纯字段赋值 + `continue`） | 同左（无 Packet） | 0 |
| `jump recurse` 自回边每层 | `Box::pin` ≈ 30–60 ns | + 85–90 ns | 0 |
| `jump recurse` 跨 Cell 内联 | ≈ 1 ns | + 85–90 ns | 0 |
| `jump and` 每实例 | spawn ≈ 100–250 ns | + 85–90 ns | 线程直调 ≈ 0 |
| `read with` 一次转发 | **12.2 – 12.8 ns（实测）** | 同左（Arc 成本与是否类型擦除无关） | 0 |
| `read with` 三层转发 | **≈ 37 – 38 ns（3 × C1）** | 同左 | 0 |

> 口径统一说明：上表"类型擦除路径"的 +85–90 ns 是**实测场景**（2 个 POD 实参 → 1 次 `Vec` 分配 + 480B memset，无 `Box`）。若实参是大对象（`Box`/`Arc`），还要叠加 2 次 `Box::new` 分配，约 +30–60 ns。§2.2 提到的"3 次堆分配"是**大对象场景**的口径，两者不要混用。

**这组实测数据的决定性含义**：

- 单次跳转的业务计算只要低于 ~1 µs，类型擦除路径就**达不到** §17 的 ≥90% 门禁（1 µs 时仅 92.3%，且是擦线）；
- 业务计算 100 ns（轻量 Cell，§12.8 承认的高频场景）时只剩 **54.7%**；
- 业务计算 10 ns（纯转发型拓扑 Cell）时只剩 **11.8%**。

也就是说：**按文档字面实现类型擦除，≥90% 只在"每个 Cell 都是 ≥1 µs 重活"的程序里偶然成立**。只要出现轻量 Cell 的高频跳转，性能就崩到 50% 以下。S2 因此不是优化项，而是**达成验收标准的必要条件**。

### 4.2 分档预估（对照 §17.2 / §10.1）

| 场景 | 文档预估 | 我的模型预估 | 达标条件 |
| --- | --- | --- | --- |
| `jump loop` 迭代 + 纯 `go with` + 类型确定 | 95–100% | **98–100%** | 采用 S2；无 Packet |
| 普通 `jump` / 少量 `recurse`，`go with` 为主 | 90–95% | **92–99%** | 采用 S2 + D3 内联；单跳业务 ≥ 1 µs 时差距不可见 |

**结论**：S2 是 ≥90% 的**必要条件**，不是优化项。按文档字面的类型擦除实现，第一档和第二档就达标不了。

### 4.3 三大性能风险与缓解

1. **类型擦除（最大固定开销）** → S2 已消除；`--dyn-packets` 保留但默认关闭。
2. **自递归 `async fn` 装箱（B9）** → 每层一次堆分配。缓解：把"每层业务 ≥ 300 ns"写进最佳实践；`Box::pin` 而非 spawn（省掉调度器）。
3. **`jump and` 小任务调度开销** → 缓解手段（按优先级）：
   - **同步相邻优化**：若 `jump and/recurse` 的**下一条语句就是** `jump sync <同一 group>`，则父在其间无任何操作，可生成内联 await 而不 spawn（语义等价证明：父在 spawn 与 sync 之间无可观测行为）。A.2 阶乘 recurse 版正是这个形状 → 直接变成 ~0 开销。
   - **协作式 join**：组内子任务数静态已知且 ≤ 阈值时，生成"父任务内轮询子 future"的 join combinator（零任务分配、零调度器参与），代价是不跨核并行。对 I/O 密集的小 Cell，调度开销常常大于并行收益，这是净赚。
   - 真并行（spawn 到 worker 线程）保留给大任务 / CPU 密集场景。
4. **增量回收（D4）** → 保证 `over` 场景内存 O(并发上限) 而非 O(元素数)。
5. **`jump` 链深度** → 长链会产生深层嵌套 future（§1.2 栈/堆真相第 1 条，已实测无 TCO）。缓解：gen 在 M7 对"叶子 Cell"做函数体内联（§12.8），把链压平。

### 4.4 基准方案（§17.3 落地）

为保持零依赖，`criterion` 不用，自建计时：

- 每个代表性场景（附录 A.1–A.8）写一份**手写等价 Rust**（`fn main` 直接循环），作为对照组；
- 两侧都用 `std::time::Instant` + N 次预热 + M 次采样取中位数，输出比值 `t_rscel / t_handwritten`；
- 门禁：比值 ≤ 1.11（= ≥90%），场景清单固定、结果写入 `docs/bench/` 留档；
- 门禁脚本 `scripts/bench.ps1`，CI/本地同一条命令。

### 4.5 已执行的选型基准（2026-09-27）

为验证 S2 本身（而不是等 M7），本报告先做了一次**单点基准**，直接对比两种调用约定在同一条 `jump` 边上的固定成本：

- 程序：20 个全局键、2 个 `i64` 实参的 plain `jump`；
- 编译：`rustc --edition 2021 -O`，无依赖；
- 方法：预热 10 万次，500 万次循环取均值，`std::hint::black_box` 防优化消除，`#[inline(never)]` 防止跨函数优化抹平差异；
- 结果见 §4.1：类型擦除 85–90 ns vs 类型化 1.0–1.2 ns，**69–89 倍**；`read with` 一次转发 12.2–12.8 ns。
- 本基准同时测了 `Arc` 的 1inc+1dec / 2inc+2dec 两档，用于**验证线性并校准单价口径**（初稿曾因口径错误把 `read with` 成本高估 3.7 倍，见 §4.1 的更正框）。

该基准的源码保留在仓库 `scripts/bench/` 下（随 M7 的完整基准一起提交），任何人可用同一条命令复现：

```powershell
rustc --edition 2021 -O scripts/bench/packet_overhead.rs -o target\bench\packet_overhead.exe
.\target\bench\packet_overhead.exe
```

> 说明：本次只测了**选型决策所需的单点**，不是 §17.3 的完整验收基准。完整基准（每个附录 A 场景 vs 手写等价 Rust，门禁比值 ≤ 1.11）仍在 M7 产出。
